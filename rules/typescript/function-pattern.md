# 関数の編集ルール

## 切り出し基準

1. 一箇所だけで使う処理は原則インラインにする。ただし、展開すると主処理を追いにくくなる独立した処理は、入出力と責務が明確で、呼び出し元との比較で読みやすさを説明できる場合に切り出してよい。
2. 複数箇所で使う場合も、見た目が似ているだけで共通化しない。同じ責務・変更理由を持つことを確認し、既存の配置・命名へ合わせる。`utils.ts`を機械的に新設しない。
3. 複雑な条件は意味の分かる変数名で整理する。条件数・行数・ネスト数だけを理由に関数境界を作らない。

## コメント

1. ヘルパー関数の作成時は、関数の先頭に処理内容をコメントで記述する
   - Why: 実装を読まなくても意図が伝わるようにし、再利用判断のコストを下げるため
```typescript
// ダメな例
// details 中から必要なデータを filter() して sort() する関数

// 良い例
// 明細データの中から割引データを除き、金額の高い順に並び替える関数
```

## 型

1. 戻り値の型は極力推論させる
  - ただし、戻り値の型が分岐する場合は、明示的に戻り値の型を定義する

## 配置

1. 最寄りの同型実装の配置・export・宣言順に合わせる。`schema.ts`、`service.ts`、`utils.ts`などの名前は、そのプロジェクトで置かれている内容と照合する。
2. 新設する関数・型・ファイルには、現在の利用箇所とその責務へ置く理由を示す。テストの都合だけでexport、依存注入引数、独自Client型を追加しない。

## スタイル

1. 可読性を優先し、宣言的な書き方を選ぶこと
  - 例: **reduce()** ではなく **filter().map()** を使う
  - ただし、パフォーマンスが計測上ボトルネックになっている箇所には適用しない
