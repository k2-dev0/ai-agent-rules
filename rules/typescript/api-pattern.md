# API の追加・編集ルール

## 実装方針

1. 複数の書き込みを一体で成功・失敗させる必要がある場合は、プロジェクトのtransaction方式を使う。単一の原子的書き込みを、形式だけのためにtransactionで包まない。
  - interactive transaction（コールバック形式）を基本とする
  - Why: 部分的な書き込みによるデータ不整合を防ぐため
2. ソート順は既存APIと利用者の要求へ合わせる。降順が固定の要件ならその順序で返し、切り替える利用箇所がないのにsort引数やUI側のreverseを増やさない。

## DB クエリのアンチパターン

1. DB から取得したデータを filter() している場合は、WHERE 句で絞れないか検討すること
  - WHERE 句で絞れる場合 → クエリを修正する
  - 複雑なクエリが必要な場合 → filter() を維持してよいが、コメントで理由を残す
  - 判断に必要なDB条件・callerを調べ、挙動や性能上のtrade-offが要件から決まらない場合だけ相談する
  - そもそもクエリが複雑になりすぎる場合は、テーブル設計の見直しを検討する
