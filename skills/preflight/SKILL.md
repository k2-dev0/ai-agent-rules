## 条件

開始時に[判断基準](../IMPLEMENTATION_RULES.md)と該当規約を読む。ファイル、Git、DB、外部サービス、依存関係を変更せず、結果は会話内へ返す。ユーザーへ直接質問しない。

調査・要件判断は[agent_name]が行い、サブエージェントへ調査を委任しない。確認済み事実は`path:line`を付け、推論・未確認と区別する。

## 手順

1. 引数と直前の会話から目的、対象、制約、期待挙動を抽出する
   - 対象が曖昧なら`scope_required`と候補をmeetingへ返す
2. 要件を次の表で分類する
   - 目的と実装手段を分け、由来不明の項目は確定しない
3. 識別子・path・固有名詞から、caller、callee、schema、test、data flow、永続化、外部境界を辿る
   - 必要な範囲だけ読み、実装・テスト・文書・履歴の食い違いを確認する
4. 下表の観点で反証する
   - 該当しない観点や根拠のない問題は列挙しない
5. 実行境界を新設する場合は、境界を新設しない基準案を作り、要件充足をコードで確認する
6. 未決定事項を影響順にmeetingへ返す
   - 回答後は副作用・既存回答との矛盾を再確認する

| 要件の由来 | 扱い |
|---|---|
| **明示要件** | ユーザーが指定した結果・挙動 |
| **禁止・制約** | 守る境界。別手段の採用義務へ読み替えない |
| **受入済みtrade-off** | ユーザーが受け入れた副作用 |
| **既存制約** | コード・data・運用・platformで確認した制約 |
| **設計選択** | 変更・破棄できる候補手段 |

| 調査観点 | 確認対象 |
|---|---|
| 既存経路 | 重複・競合・責務、deployment・scheduler・route・worker・監視・復旧の再利用 |
| 契約 | 利用者・caller・公開API・型・schema・設定・互換性 |
| 状態・失敗 | 整合性、migration、並行実行、冪等性、部分失敗、error・fallback・再試行・rollback |
| 安全性・運用 | 認証・認可・入力・機密・監査、性能・容量・rate limit・timeout |
| 検証 | 正常・異常・境界値、完了条件、段階的rollout、手段の過不足、制約の衝突 |

移植では両リポジトリを調べ、不具合・未完成処理・環境依存・version・license・テスト不足を比較する。参照できない範囲は未確認とする。

## 返却

論点ごとに「重大度、確認済み／推論／未確認、path:line、問題、影響、必要な判断・選択肢・挙動差・推奨」を簡潔に示す。問題がなくても調査範囲・棄却した仮説・未確認範囲は返す。

目的・対象、分類済み要件、既存の実行方式、基準案、受入済み副作用、持ち越す未確認事項を次のstatusとともに返す。根拠不足は推測で補わない。

| status | 条件 |
|---|---|
| `preflight_ready` | 必須調査が済み、重大な未決定事項がない |
| `consultation_required` | ユーザー判断が必要 |
| `blocked` | 参照先・必須根拠が不足 |
