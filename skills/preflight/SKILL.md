## 目的

ユーザーの要件には未発見の穴があると仮定し、設計前に反証的な調査を行う。
ユーザーやコードベースの正しさを採点せず、要件と既存システムの間にある衝突、副作用、曖昧さ、暗黙の前提を、判断可能な論点として返す。

## 絶対条件

- 調査と考察だけを行い、コード、テスト、設定、設計書、メモを含むファイルを一切作成・変更・削除しない
- Git、database、外部サービス、依存関係などの状態を変更しない
- 調査結果は会話内だけに出力する
- 問題があるという仮説から調査を始めるが、根拠のない問題を捏造しない
- ユーザーの意見をそのまま前提にせず、目的、手段、制約、受け入れる副作用に分けて検討する
- 既存コードも正解とはみなさない。実装、テスト、文書、履歴が食い違う可能性を調べる

## 調査の委任

コードベースの事実確認はDeepSeekの`survey`へ委任する。設計・要件・採否判断は[agent_name]が行う。
`survey`は必ず`bash [skills_root]/deepseek/delegate.sh survey`で実行する。

1. 上位モデルが、確認したい仮説、探索範囲、期待する根拠を具体的な調査項目へ分ける
2. 独立した調査項目はそれぞれ固有の task-id で固定実行器へ委任する
3. 下位モデルには変更系 tool を与えず、`file:line` の根拠、確認できない事項、反証候補だけを返させる
4. 上位モデルが重要な根拠を実ファイルで再確認する。下位モデルの自己申告だけで論点を確定しない
5. 共通契約の代替調査も使えない、または参照先がない場合は調査不能な範囲を報告し、推測で穴埋めしない

上位モデル自身による広範なコード探索を避ける。上位モデルが直接読むのは、委任内容を組み立てるための入口と、重要な根拠の再確認に必要な箇所に絞る。

## 実行フロー

### Step 1: 対象を確定する

引数と直前の会話から、目的、対象、制約、期待する挙動を抽出する。一意に決められない場合は質問せず、`scope_required` と候補を meeting へ返す。

「この方法で実装する」と「この結果を実現したい」を分ける。実装手段だけが要件化され、目的や制約が欠落していないかを疑う。

抽出した項目へ次の由来を付ける。由来が不明な項目を確定要件として扱わない。

| 由来 | 意味 |
|---|---|
| **明示要件** | ユーザーが必要な結果または挙動として指定したもの |
| **禁止・制約** | 採用してはいけない手段や守る境界。関連する別手段の採用義務には変換しない |
| **受入済み trade-off** | ユーザーが副作用を理解して受け入れたもの |
| **既存制約** | コード、data、運用、platform から確認できた変更不能または変更困難な条件 |
| **設計選択** | 上記を満たすための候補手段。要件ではなく、後段で破棄できる |

### Step 2: 事実を調査する

対象に応じて以下を調査する:

1. AGENTS.md と関連 rules にある制約
2. 同じ責務または似た挙動を持つ既存機能
3. 呼び出し元、呼び出し先、data flow、永続化、外部境界
4. 正常系、異常系、境界値を示すテスト
5. 公開 API、型、schema、設定、権限、互換性に関わる契約
6. 必要な場合だけ git log / git blame から読み取れる設計理由
7. 既存の deployment topology、scheduler、route、worker、永続化、監視、失敗復旧など、同じ結果を運ぶ実行方式

要件の単語だけを検索して終えない。責務、データ、状態遷移、利用者の導線から関連箇所を辿る。

別リポジトリからの移植では、移植元と移植先の両方を調べる。移植元の既知不具合、未完成処理、環境依存、依存 version、license、テスト不足を確認する。移植元を参照できない場合は監査不能な範囲として示す。

### Step 3: 反証仮説を検証する

「要件どおり実施すると何が壊れるか」「成立に必要なのに書かれていない条件は何か」を起点に、関係する観点だけを検証する:

- 既存機能との重複、競合、責務の分裂
- 既存利用者、呼び出し元、公開 API への後方互換性
- データ整合性、migration、並行実行、冪等性、部分失敗
- 認証、認可、入力境界、機密情報、監査可能性
- 性能、容量、rate limit、timeout、運用、監視、復旧
- error、fallback、再試行、rollback
- テスト可能性、完了条件、段階的 rollout
- 手段が目的に対して過剰または不足している可能性
- 明示された制約同士が両立しない可能性

全観点を儀式的に列挙しない。各仮説を証拠で棄却または支持する。

新しい public endpoint、queue、scheduler、worker、serverless function、外部接続、global/shared 変更を要件が直接要求していない場合は、それらを追加せず既存の実行方式と必要最小限の永続化だけで実現する基準案を一つ作る。基準案が要件を満たせない場合は、満たせない要件とコード根拠を示す。新しい境界の方が高性能・低遅延というだけでは、その性能が明示要件でない限り採用理由にしない。

### Step 4: 論点を報告する

各論点を **確認済み**、**推論**、**未確認** のいずれかに分類し、影響の大きい順に出力する。

```
### [重大 | 注意 | 軽微] 論点
- 区分: 確認済み | 推論 | 未確認
- 根拠: path/to/file:line
- 穴: 要件に含まれていない条件、衝突、または副作用
- 影響: 未解決のまま設計した場合に起きること
- 確認事項: ユーザーが決める必要のある一つの判断
```

有力な問題を発見できなかった場合も「問題なし」で済ませず、調べた範囲、棄却した主な仮説、調べられなかった範囲を報告する。

### Step 5: 必要な判断を返す

未決定事項を影響の大きい順に並べ、選択肢、挙動差、推奨を meeting へ返す。ユーザーへ直接質問しない。meeting から回答を受け取った場合は、その選択で新たに生じる副作用や、既存回答との矛盾がないかをもう一度検討する。

副作用を理解した上で受け入れる判断は、明示的な制約として確定する。ユーザーの選択を覆すこと自体を目的にしない。

### Step 6: meeting へ引き渡す

目的と対象範囲、由来を付けた要件・制約・設計選択、既存の実行方式、境界を新設しない基準案、重大な副作用への判断、受け入れる trade-off、未確認のまま持ち越す事項を会話内に要約する。ファイルには保存しない。

結果を次の status とともに meeting へ返す。

| status | 意味 |
|---|---|
| `preflight_ready` | 重大な未決定事項がなく、cowlick へ渡せる |
| `consultation_required` | ユーザー判断が必要な論点がある |
| `blocked` | 委任手段、参照先、根拠が不足し、監査を続行できない |
