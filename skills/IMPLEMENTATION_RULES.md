# 設計・実装・レビューの判断基準

- 設計・実装・レビューを始める前に、対象に該当する下表の規約を読む。配布先では`.[agent_name]/rules/`、配布元では`rules/`を基準にする。Markdownを置いただけでCodexが自動適用すると考えない。
- 最寄りの同型実装、caller、export、依存関係、既存の検証・mock方式を確認し、そのプロジェクトでの配置・命名・宣言順へ合わせる。`schema.ts`、`service.ts`等の一般的な意味だけで配置を決めず、規約に書かれたライブラリやpathの存在を仮定しない。
- ユーザーの明示要件と、設計書が提案した実装手段を区別する。既存実装と矛盾する古い規約・設計案は根拠付きで訂正し、承認済みの挙動を変える場合だけユーザー判断へ戻す。
- 読み込み済みの規約、採用する既存例、食い違いの解決を作業の説明に簡潔に残す。委任する場合は、適用する規約と既存例も実装指示へ渡す。

## 構造の判断

- 現在の呼び出し元と要件から必要性を説明できる関数・型・ファイルだけを追加する（YAGNI）。テストのためだけのexport、Client差し替え引数、独自のClientLike型、薄いwrapper、将来用の設定は追加しない。同一file内の呼び出しもconsumerとし、外部consumerを作るために公開範囲を広げない。
- 一度しか使わない処理は原則インラインにする。展開すると主処理の理解が難しくなる独立した処理は、入出力・責務を明確にし、呼び出し元との比較で読みやすさを説明できる場合に切り出してよい。行数やネスト数だけで関数境界を作らず、複雑な条件は意味の分かる変数名で整理する。
- 複数箇所で使う処理も、見た目が似ているだけで共通化しない。同じ責務・変更理由を持つことを確認し、`utils.ts`等を機械的に新設しない。
- HTTP、ファイル、外部APIなどの未検証入力は境界で検証する。検証済みの内部値に対して、起こり得る経路の根拠なく型を広げたり、重複guard・黙ったfallbackを足したりしない。
- 半年後の保守者が制御フローとデータ変換を上から追える直線的な実装を優先する。不要なhelperによる関数ジャンプを増やさず、多少冗長でも局所的に理解できる名前と構造を選ぶ。言語固有の記法は上表の該当規約に従う。
- テスト・型検査の成功と、構造・配置・命名の妥当性を別々に判定する。新設要素の利用箇所、単純な代替との比較、同じ責務の既存例を根拠に採用する。

## 実行境界を新設する場合

新しいpublic endpoint、queue、scheduler、worker、serverless function、外部接続、global/shared変更は、既存の実行方式と必要最小限の永続化だけを使う基準案で満たせない明示要件または既存制約がある場合だけ採用する。対応要件、境界を新設しない代替案、その案では満たせないコード根拠を揃える。明示要件でない即時性・性能・将来の拡張性だけを採用理由にしない。
