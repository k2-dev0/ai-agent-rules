# 設計・実装・レビューの判断基準

- 設計・実装・レビューを始める前に、対象に該当する下表の規約を読む。配布先では`.[agent_name]/rules/`、配布元では`rules/`を基準にする。Markdownを置いただけでCodexが自動適用すると考えない。
- 最寄りの同型実装、caller、export、依存関係を確認し、そのプロジェクトでのディレクトリ・ファイル名の意味と照合する。規約に書かれたライブラリやpathの存在を仮定しない。
- ユーザーの明示要件と、設計書が提案した実装手段を区別する。既存実装と矛盾する古い規約・設計案は根拠付きで訂正し、承認済みの挙動を変える場合だけユーザー判断へ戻す。
- 読み込み済みの規約、採用する既存例、食い違いの解決を作業の説明に簡潔に残す。委任する場合は、適用する規約と既存例も実装指示へ渡す。

## 設計とレビュー

- 現在の呼び出し元と要件から必要性を説明できる関数・型・ファイルだけを追加する。テストのためだけのClient差し替え引数、独自のClientLike型、薄いwrapper、将来用の設定は追加しない。
- 一度しか使わない処理は原則インラインにする。インライン化すると主処理の理解が難しくなる独立した処理は、呼び出し元との比較で理由を説明できる場合に切り出してよい。行数やネスト数だけで決めない。
- 外部入力は境界で検証する。検証済みの内部値に対して、起こり得る経路の根拠なく型を広げたり、重複検証・fallbackを足したりしない。
- テスト・型検査の成功と、構造・配置・命名の妥当性を別々に判定する。新設要素の利用箇所、インライン案との比較、同じ責務の既存例を確認してから採用する。
