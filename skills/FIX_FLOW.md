# 診断・指摘への修正手順

## 診断のscope帰属

test・typecheck・lint・Prisma・buildの診断を分類する。終了codeだけで判定しない。

| 分類 | 条件と対応 |
|---|---|
| `scope-related` | 選択済み対象test、関連する既存test、実変更path、変更した公開型・export・契約に起因するcallerの失敗。追跡状態・今回の編集有無を問わず修正・再検証し、解消できなければ`scope fail` |
| `unrelated` | 今回の要求・変更と無関係と確認した既存失敗。対象外fileを変更・削除せず、command・diagnostic・無関係と判断した根拠を報告して続行 |
| `uncertain` | 因果関係を確定できない失敗。成功・失敗を推測せず報告 |

どの分類が残っていても完了マークを自動判定せず、ユーザー判断に従う。

ignored / untrackedやcheckout前からの存在だけで`unrelated`にしない。関連fileの所有・追跡方針が未決定なら[作業対象の扱い](IMPLEMENTATION_RULES.md#作業対象とgit状態)へ戻る。

## 修正ループ

Codexは下の「Codexの修正担当」を使う。以下のモデル再評価・メイン直接修正はClaudeだけに適用する。

1. 診断・指摘の箇所と成立条件を確認し、原因と必要な判断を特定する
2. 修正着手前に[メインモデル選択](MODEL_SELECTION.md)の再評価条件を適用する
   - 同じ方針なら評価結果を再利用する
   - 直前レビューと同じfile内の関数・section・testへの指摘が再発した場合は、内容・severity・行番号にかかわらずLunaからSol、SolからAstraへ昇格し、Astra / xhighでは維持する
   - [実装基準](IMPLEMENTATION_RULES.md)が未読または文脈から失われた場合だけ読み、メインが指摘範囲を直接修正する
   - 選択済みシナリオを保つテスト修正は直接行い、シナリオ変更は呼び出し元の再選択手順へ戻す
3. 影響するtest・静的検査・整形を実行する
   - 失敗が残ればStep 1へ戻り、検証結果と未解決事項を報告する
   - 実行不能な検証は未実行とする
4. 追跡対象をGit規約どおりcommitし、呼び出し元へ戻る

失敗時は原因と未解決の判断を再確認する。同じ方針の再試行回数だけでモデルや修正主体を変えない。

## Codexの修正担当

診断・成立指摘は通常DeepSeekへ渡す。新しい設計判断は親が[作業分担](WORKFLOW_ROUTING.md)に従って確定する。severityによる採否・ユーザー確認は`INDEPENDENT_REVIEW.md`に従い、修正対象に採用された指摘だけ処理する。

直前の有効なレビューと修正後レビューを比較し、同じfile内の関数・section・testへの成立指摘が再発した箇所だけ、主担当Astra / xhighへ移管する。行番号・内容・severityの変化では別箇所にしない。同一レビュー内の複数指摘・同一HEADの再取得・却下・incompleteは2回と数えない。

- 初回箇所はDeepSeek、再発箇所と修正に直接必要なtest・依存だけはAstraが担当する
- 一部の再発をfile・レビュー・タスク全体のAstra移管へ広げない；分離不能な不変条件・共通依存だけ最小範囲でAstraへ含める
- 親が「path＋関数／section／test」、採否、前回修正担当、今回担当を保持し、briefには各担当の修正範囲と変更禁止箇所を渡す；過去レビューは独立reviewerへ渡さない
- DeepSeek修正→停止・検証結果と禁止範囲の照合・commit→Astraの限定修正の順で直列実行する；同一fileでも独立した箇所は分担する
- Astra修正後の結合状態で、DeepSeekが関連検証だけを実行する；再発箇所をworkerへ再修正させない；親はGit処理後に新しい独立レビューへ戻る
- Astra修正後も同じ箇所へ成立指摘が再発したら、その箇所の自動修正を止めて未解決報告する；独立した他箇所は続行できるが、未解決部分を完了扱いしない

単なるtest失敗回数や別箇所の指摘回数でAstraへ移管しない。
