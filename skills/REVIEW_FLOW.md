# 実装レビューと再実装

初回実装後に[実装契約](IMPLEMENTER_CONTRACT.md)と[判断基準](IMPLEMENTATION_RULES.md)・該当規約を読み、共有worktreeの実差分を全件レビューする。自己申告や想定変更先だけで判定しない。

| レビュー対象 | 確認 |
|---|---|
| 要求 | 全要件の実装、範囲外変更、追加pathの必要性 |
| 品質 | 構造・配置・命名・契約・副作用、テスト攻略の有無 |
| テスト資産 | 親が管理。選択済みシナリオの実現に必要な修正は直接行い、シナリオ変更は本体修正前にユーザーの再選択へ戻す |

## 診断のscope帰属

test・typecheck・lint・Prisma・buildの診断を分類する。終了codeだけで判定しない。

| 分類 | 条件と対応 |
|---|---|
| `scope-related` | 選択済み対象test、実変更path、変更した公開型・export・契約に起因するcallerの失敗。下記ループで修正・再検証し、解消できなければ`scope fail` |
| `unrelated` | 無関係な既存失敗、今回未変更のignored / untracked test、checkout前の残留test。対象外fileを変更・削除せず、command・diagnostic・根拠を報告して続行 |
| `uncertain` | 因果関係を確定できない失敗。成功・失敗を推測せず報告 |

どの分類が残っていても完了マークを自動判定せず、ユーザー判断に従う。

## 修正主体

変更行数は最小修正案の追加行＋削除行。置換1行は2行、contextとformatter・linterの自動差分は除く。実差分が見積もりを超えたら再分類する。

| 判定 | 条件 | 担当 |
|---|---|---|
| 小さい問題 | 1ファイル、変更行数が10行以下、一意なtypo・import・書式・lint・機械的型修正で、挙動・公開契約・永続化を変えない。すべて満たす場合だけ | 親が直接修正 |
| 大きい問題 | 変更先が2ファイル以上、または変更行数が11行以上。制御フロー・業務ロジック・データ変換・計算・状態遷移・error・公開API/型・schema・永続化・transaction・並行制御・認証認可・securityを変える。新しい仕様解釈・設計・architecture判断が必要。一つでも該当 | 修正方針を確定し、下位モデルに再実装させる |

1行の条件反転でも挙動が変われば大きい問題。修正候補が複数ある場合も大きい問題とし、仕様・設計を確定してから委任する。

## 修正ループ

1. 全差分をレビューし、指摘ごとに大小を判定する。
2. 小さい問題は直接修正。大きい問題は「箇所・影響・不変条件・修正方針・完了条件・変更禁止範囲・test command」をbriefへまとめ、[起動手順](IMPLEMENTER_LAUNCH.md)で再実装を委任する。
3. 下位モデルは指摘範囲だけを修正し、指定testを実行する。親は実差分を全件再レビューする。
4. 対象test、必要な静的検査、formatter、lint後に最終レビューする。新しい指摘はStep 1へ戻し、修正後は影響する検証を再実行する。

同じ箇所・同じ不変条件の再実装が2回連続で失敗した場合だけ、親が大きい問題を直接修正できる。別箇所・別条件・新規問題は回数に含めない。直接修正後もテストと最終レビューを行う。

## 報告

初回レビューはGreen、formatter、lint、polish、本体コードのcommitより先に、次の3項目だけを簡潔に報告する。

- 採用: 採用する変更
- 問題: 箇所・影響・採用／修正／拒否
- 修正主体: 大小判定と担当

該当なしは「なし」とする。コードの再掲、作業手順、内部推論は報告しない。報告後、追跡対象の本体変更をGit規約どおりコミットする。
