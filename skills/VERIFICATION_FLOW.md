# 検証失敗の分類と修正

## 診断のscope帰属

test・typecheck・lint・Prisma・buildの診断を分類する。終了codeだけで判定しない。

| 分類 | 条件と対応 |
|---|---|
| `scope-related` | 選択済み対象test、実変更path、変更した公開型・export・契約に起因するcallerの失敗。下記ループで修正・再検証し、解消できなければ`scope fail` |
| `unrelated` | 無関係な既存失敗、今回未変更のignored / untracked test、checkout前の残留test。対象外fileを変更・削除せず、command・diagnostic・根拠を報告して続行 |
| `uncertain` | 因果関係を確定できない失敗。成功・失敗を推測せず報告 |

どの分類が残っていても完了マークを自動判定せず、ユーザー判断に従う。

## 修正ループ

1. 診断・指摘の箇所と成立条件を確認し、原因と必要な判断を特定する。
2. [モデル選択](MODEL_SELECTION.md)で残作業を再判定し、[実装基準](IMPLEMENTATION_RULES.md)に従ってメインが指摘範囲を直接修正する。選択済みシナリオを保つテスト修正は直接行い、シナリオ変更は呼び出し元の再選択手順へ戻す。
3. 影響するtest・静的検査・整形を実行する。失敗が残ればStep 1へ戻り、検証結果と未解決事項を報告する。実行不能な検証は未実行とする。
4. 追跡対象をGit規約どおりcommitし、呼び出し元へ戻る。独立レビューの起動時点は[独立レビュー](INDEPENDENT_REVIEW.md)に従う。

失敗時は原因と未解決の判断を再確認する。同じ方針の再試行回数だけでモデルや修正主体を変えない。
